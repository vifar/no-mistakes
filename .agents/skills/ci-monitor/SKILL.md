**CI Monitor Lifecycle**

- The CI step produces findings, not fixes: a settled observation returns one finding per issue with an `action` (`ciObservationFindings`, `internal/pipeline/steps/ci_findings.go`) and the executor's shared auto-fix loop drives fix rounds (`repairFromFindings` in `ci_fix.go` consumes `sctx.PreviousFindings`), so `auto_fix.ci` is counted by the executor from round history and a review-bot check (`scm.ReviewBots`, identified by `scm.Check.App`) parks as `ask-user` comment findings without spending a round. A published repair keeps monitoring inside the fix round and must call `sctx.MarkRunning()` so status returns to `running` for the readiness consumers. "CI Step Findings Model" below owns the contract and regression list.
- `ci_timeout` is an idle timeout, not an absolute deadline: only `timeoutAnchor` re-arms when the upstream default-branch tip advances, `started` stays fixed for poll pacing, and re-arm only ever extends the deadline (fail-safe on transient base-tip failures). Value semantics (`0` unset, negative unlimited sentinel, keyword parsing) live in `config.go`; keep `config.DefaultCITimeout` and `defaultConfigYAML` in sync (`TestDefaultConfigYAML_MatchesGoDefaults`). User-facing semantics are owned by `docs/src/content/docs/reference/global-config.md`.
- GitHub check collection is the union of the exact current PR head commit's check rollup and every Actions workflow run returned by the Actions API for that same SHA, before the check scope below is applied. A workflow rejected before creating jobs/check-runs is absent from the commit rollup but still present in that API; run discovery errors and unknown run states fail closed instead of certifying a green rollup. Regressions: `TestGetChecksIncludesFailedWorkflowRunMissingFromPRRollup`, `TestGetChecksBindsRollupAcrossABAHeadMovement`, `TestCIStep_FailedHeadWorkflowRunPreventsChecksPassed`.
- GitHub's raw commit `statusCheckRollup` returns every check run a commit ever had, including a same-named run a later run at that same head has already superseded (e.g. a required-check job re-triggered by `synchronize` after a pipeline auto-fix push). `Host.GetChecks` (`internal/scm/github/github.go`) collapses same-name reruns of one workflow to the newest attempt (`attemptAfter`, using the attempt start before the job start and Actions run identity to break timestamp ties, comparing against every retained duplicate, and preserving unordered records, including ambiguous pending replacements, before a `completedAt` fallback) while preserving independent workflows, unidentified external checks, and other same-named commit status contexts (the pipeline status exclusion is owned by [Push](../../../docs/src/content/docs/reference/pipeline-steps.md#push)), restoring the semantics `gh pr checks` already applies and this repo's own gate `verify.py` already assumes (last-wins). Collapse must run AFTER `appendUnrepresentedWorkflowRuns`, never before: that call reconciles the Actions-run union with job checks by run ID over the FULL uncollapsed rollup, so collapsing first drops a superseded run's ID out of the "represented" set and the union re-adds the same stale run under its own workflow run name. That same call also retires stale attempts and preserves their job identities on blocking workflow-level replacements before collapse; its function comment owns the attempt rules (`TestGetChecksSupersedesSameNameJobBeforeCollapsing`). Without this collapse, a monitor that keeps `synchronize` in its gate trigger set can loop forever: each auto-fix push legitimately fails the gate at the old head, a later same-head rebind turns it green, but the stale FAILURE stays visible and re-triggers another auto-fix round. Regressions: `TestGetChecksCollapsesSupersededSameNameCheckToLatestAtOneHead`, `TestGetChecksCollapseOrderingDoesNotLetWorkflowRunUnionResurrectSupersededCheck`, `TestGetChecksPreservesIndependentSameNameWorkflows`, `TestGetChecksPreservesIndependentSameNameExternalCheckRuns`, `TestGetChecksCollapseComparesNewestRunWithEverySameNameCandidate`, `TestGetChecksKeepsQueuedReplacementWithEqualStartTime`, `TestGetChecksPreservesUnorderedExternalPendingReplacement`, `TestGetChecksPreservesSameNameStatusContextAndCheckRun`.
- `publishRepair` uses `publishRunHead` and its shared pre-push attestation boundary; the [PR publication safety skill](../pr-publication-safety/SKILL.md#pre-push-pipeline-attestation) owns that implementation map. The CI fixer prompt may conclude that a stale/attestation/infrastructure red is not a code defect; a genuine failing test or build must still be fixed. Regressions: `TestCIStep_PublishRepairRebindsAttestationAcrossRepairPushes`, `TestCIStep_PublishRepairDoesNotMintAttestation`, `TestCIStep_PublishRepairSkipsRestampWithoutReader`, `TestCIStep_FixPromptPrefersSimplificationOverMachinery`, `TestCIStep_FixPromptDistinguishesCodeDefectFromExternalFailure`.
- CI readiness never treats an unproven empty forge check list as green. `scm.ScopedChecks.Ready` distinguishes an observed, entirely excluded rollup from no observed checks; `internal/pipeline/steps/ci.go` separately applies the ordinary-run empty-rollup exception. The [`ci.required_checks`](../../../docs/src/content/docs/reference/repo-config.md#cirequired_checks) and [`no_ci`](../../../docs/src/content/docs/reference/repo-config.md#no_ci) references own the user-facing rules; `internal/cimonitor` owns the agent-facing log vocabulary and Ready/DeclaredNoCI parse. Regressions: `TestChecksPassed_PR607RealLogSequence`, `TestCIStep_EmptyChecksWithoutNoCIStaysNotReadyPastOldGracePeriod`, `TestCIStep_EmptyChecksWithTrustedNoCIBecomesReady`, `TestCIStep_DelayedCheckRegistrationStaysNotReadyUntilGreen`, `TestCIStep_DeclaredNoCIWithUnexpectedChecksHonorsThem`, `TestEffectiveRepoConfig_NoCITrustedOnly`, `TestCheckScopeReadinessDistinguishesExcludedFromUnobserved`, `TestStrictCIExternalOnlyReadiness`, `TestCIReadyReceiptExternalOnlyUsesSharedReadiness`.
- Persistent provider check-read failures are not an invisible spin: 6 consecutive `GetChecks` errors while the PR is still open park the CI step at an ask-user gate whose provider-neutral finding names the provider CLI/credentials support and includes the underlying error (with a GitHub-specific clause requiring `gh` >= 2.50 for the `gh pr checks --json` call), and the streak resets on any successful read. Regression: `TestCIStep_PersistentCheckReadFailureParksAtAskUser`.
- Reap an orphaned monitor from outside its worktree with `no-mistakes axi abort --run <id>`; it needs only `NM_HOME` and never starts a stopped daemon. A known run succeeds only with durable terminal truth, a recorded nonterminal run fails unconfirmed, and only an unknown id is an idempotent no-op. Bare `axi abort` stays worktree/branch-scoped.
- A merged or closed PR observation records lifecycle facts only. The executor completes CI and the run after current support proof and the final live PR comparison pass; stored terminal state never substitutes for those checks. Crash recovery preserves reconstructible parked gates and leaves unverified active CI runs interrupted. Owners: `terminalCIOutcome`, the executor completion boundary, and `GuardPRContext`; startup semantics are owned by `concepts/daemon.md`.
- A provider-reported `cancelled` check is never a job verdict, so the deterministic rerun runs strictly before any CI fix round: cancellation and a GitHub pre-run infrastructure failure (a job that failed in setup/action resolution before any repository step ran, flagged `Check.PreRunFailure` by the opt-in `scm.PreRunFailureDetector` and re-bucketed to cancel so it never masks a real test/lint failure, which cleared setup and failed a later step) are the outcomes that earn a rerun, either outcome after its budget parks as `ask-user` instead of entering the `auto_fix.ci` loop, and any genuine or unrecognized failure or merge conflict in the same poll suppresses reruns so real failures still escalate on their first observation. The budget is per check name per run and spent on request rather than on success, and a rerun is never issued once the published branch head no longer equals `runs.head_sha`, because it would certify a commit this run never delivered. Each outstanding rerun records its verified pipeline head and the same-name provider links visible when it was requested; it retires durably when the run head advances or a new conclusive non-cancel link appears. Retirement keeps the spent budget and never changes check buckets. A delayed same-named green sibling can satisfy the link trigger on the same head, matching the default branch's existing name-keyed masking; removing that limitation requires provider truth outside this policy. Classification, the deliberate `TIMED_OUT`/`STALE` exclusions, rollup-lag grace, and retirement live in `internal/pipeline/steps/ci_transient.go`; provider support is the optional `scm.CheckRerunner` (GitHub only), pre-run infrastructure detection is the optional `scm.PreRunFailureDetector` (GitHub only, folded in by `markPreRunInfraFailures`), and user-facing semantics are owned by `docs/src/content/docs/reference/repo-config.md`. Regressions: `TestCIStep_CancelledCheckIsRerunBeforeEscalating`, `TestCIStep_CancelledCheckStaysUnresolvedAfterItsBudget`, `TestCIStep_LaggingRerunRollupKeepsWaitingForTheRepublishedCheck`, `TestCIStep_SameHeadGreenRerunEmitsChecksPassed`, `TestCIStep_DelayedSameNameCheckRetainsLegacyNameBehavior`, `TestCIStep_ResolvedRerunDoesNotParkALaterGreenHead`, `TestRetireResolvedReruns`, `TestRetireResolvedRerunsRetriesAfterPersistenceFailure`, `TestCIStep_MovedPublishedHeadTerminatesInsteadOfRerunning`, `TestCIStep_MovedPublishedHeadClearsCIReadiness`, `TestClassifyCheckFailure`, `TestMarkPreRunInfraFailures_RetriesInfraButNotGenuine`, `TestMarkPreRunInfraFailures_OptInGated`, `TestPreRunFailures_FlagsSetupFailureNotGenuine`, `TestPreRunFailures_FailsClosedOnUnreadableRun`.
- **Terminal is not pending.** `scm.ScopedChecks.Settled` rejects every in-scope non pass/fail/skip bucket, but only checks that can still finish on their own (`hasExecutingPendingChecks`) may defer escalation. A GitHub run held for maintainer approval (`scm.Check.AwaitingApproval`: `action_required` with no jobs) is pending for readiness but never defers another check's failure (`internal/pipeline/steps/ci_awaiting_approval_test.go`). Synthetic missing requirements (`scm.Check.ExpectedMissing`) also block readiness without deferring escalation or proving a post-repair execution; regressions: `TestCIStep_MissingRequiredCheckDoesNotDelayBuildRepair`, `TestMissingChecksDoNotCountAsExecutingOrVerifyRepairs`. A `cancel` bucket - GitHub `CANCELLED`, GitLab `canceled`, Bitbucket `STOPPED`, and how GitHub reports a job killed by its own `timeout-minutes` - is a published conclusion that nothing will replace, so with no rerun outstanding it is reported as an `ask-user` transient finding (`unresolvedTransientFindings`, selected by `cancelledWithoutRerun`) instead of waiting. Conflating the two is the #628 regression that hung real runs for their whole `ci_timeout`; an unrecognized bucket is deliberately still treated as waiting, because unknown is not evidence of terminal. Regressions: `TestCIStep_CancelledCheckAmongPassingChecksEscalatesInsteadOfPollingForever`, `TestCIStep_ZeroRerunBudgetEscalatesCancelledCheckWithoutMakingItReady`, `TestCIStep_BitbucketStoppedCheckParksForADecision`.
- Ordinary CI readiness reads the provider's live PR head rollup on every poll. It compares the current PR and target against the live comparison receipt and requires provider-backed commit evidence before classifying, rerunning, or reporting any check. Missing or mismatched check heads wait without becoming repair findings; approval observations record the mismatch as an override. A published repair advances the receipt through the guarded publication boundary. Review CI claims retain their original check ID and head; after a guarded forward publication, only the owning result can move to the final receipt, with the same exact check ID and unique provider-backed evidence. Changed execution IDs without native lineage stay unresolved. Strict shipping additionally requires all check evidence and current PR facts to match its pinned comparison receipt; mismatched heads, retargets, or missing evidence clear readiness. Regressions: `TestCIStep_GreenChecksAtAdvancedHeadAreRecognizedWhileRunTracksOlderHead`, `TestCIStep_GreenChecksAtAdvancedHeadCannotCertifyOlderReceipt`, `TestCIStepLiveRetargetWithNoClaimsWithholdsReadiness`, `TestCIMonitorReadinessRequiresChecksOnReceiptHead`, `TestCIOwnerResolvesPublishedForwardClaimWithoutRelabeling`.
- **Check scope.** `CIStep.Execute` validates check heads before passing checks through one `scm.CheckScope` (`internal/scm/check_scope.go`), so readiness, the fix agent, `VerifyApprovalOverride`, and the strict `ci-ready` receipt (`shipping.Export`, which applies the policy the step recorded with `SetRunCheckScope`) judge the same set. `CheckScope` caches the target's requirements from `scm.RequiredChecksReader`; GitHub's reader refuses a partial protection/rules result; only GitHub's explicit no-classic-protection 404 (`classicProtectionAbsent`) makes protection an empty source so rulesets decide alone (`TestGetRequiredChecksReadsRulesetsWhenClassicProtectionIsAbsent`). A retarget clears the old target's timeout evidence with the scope (`TestCIStep_RetargetAtDeadlineDropsTheOldTargetsTimeoutEvidence`). The recorded scope carries the resolved required set once known (`CheckScopePolicy.Resolved`, `CheckScope.Policy`), so approval and the receipt rebuild the scope that raised the gate (`TestCIScopeApprovalReusesTheResolvedScopeThatRaisedTheGate`). Collapse never merges different triggers (`TestGetChecksCollapseKeepsJobsOfDifferentTriggers`); a green jobless rerun leaves retired required jobs missing (`TestGetChecksGreenJoblessRerunDoesNotSpeakForStaleJobs`); retained work naming the replacement keeps its aggregate role while work naming a superseded job is judged as that job alone (`TestCIScopeRetainedFindingMatchesThroughSupersededIdentity`, `TestCIScopeRetainedWorkUsesMatchedIdentity`), and a retained provider ID finds the superseded job it named before any name fallback (`TestCIScopeRetainedWorkFindsSupersededJobByProviderID`); On a rerun attempt, `currentAttemptJobs` reads the attempt's own job IDs and membership, not timing, decides which jobs are current, so a partial rerun keeps its untouched successes (`TestGetChecksPartialRerunKeepsUntouchedSuccessfulJobs`). A fix round with a carried replay awaiting its Test restart (`RunTestRestartPending`) has no published head: if the check read returns mismatched heads, it discards that observation and scopes retained work by context through `CheckScope.IncludesContext` instead (`TestCIScopeRetainedWorkWithoutProducerEvidence`). `appendUnrepresentedWorkflowRuns` judges each trigger (workflow, event, branch) by its newest meaningful attempt, ordered by `Check.AttemptStartedAt` via `attemptAfter`; the newest attempt's failing or unfinished run-level result owns every retired job it has not reported, a passing one leaves them missing, and skipped attempts never count. Collapse merges only same-named runs with a known, matching trigger (`TestCollapseRequiresAKnownMatchingTrigger`); a cancelled job whose run also reports a cancelled run-level result is folded into that run for rerun selection and cancellation handling on every poll (`foldRunCoveredJobs`, `TestTransientRerunCandidatesCoalesceOneActionsRun`). `TestGetChecksAttemptSequencesJudgeTheNewestMeaningfulAttempt` exhaustively checks attempt sequences (including partial reports and a job named like its workflow) against that rule; `TestGetChecksRerunOfAnOlderRunIDIsTheNewestAttempt`, `TestGetChecksActiveRerunOfAnOlderRunIDIsNotCollapsedAway`); a self-status-only requirement is ready on an empty rollup outside strict shipping (`TestCheckScopeSelfStatusOnlyRequirementIsReadyWithoutObservedChecks`). `ScopedChecks.Settled` also owns pending informational-bot readiness, using `ReviewBotForCheck` (app identity first, known-name fallback only without an app). The recorded `CheckScopePolicy` includes `ReviewBotComments`; `VerifyApprovalOverride` passes that policy into `greenReviewBotFindings` rather than re-reading live config. Monitoring readiness and approval verification use `scm.ReadReadinessReviewBotComments` through that wrapper; `shipping.Export` calls the same helper directly with the recorded policy. `scm.ReviewBotCommentChecks` owns the candidate set for that read and for `greenReviewBotChecks`, including the absent-bot fallback. Regressions: `TestCIReadyReceiptWaitsForRecordedReviewBotPolicy`, `TestCIReadyReceiptVerifiesRecordedReviewBotComments`, `TestReviewBotForCheckHonorsReportedApp`, `TestCIStep_VerifyApprovalOverride_RecordedReviewBotPolicy`. `ci_scope.go` applies the current scope to retained findings and outstanding reruns while preserving spent budgets. Excluded app identities reach `ReviewBotCommentChecks` so its absent-check fallback cannot resurrect an excluded bot; `Finding.CheckApp` preserves that identity for retained bot findings even without a check name. An emptied repair selection calls `MarkRunning` before monitoring resumes. The [repo config reference](../../../docs/src/content/docs/reference/repo-config.md#cirequired_checks) owns policy semantics. Never add a second place that decides which checks count.

**CI Step Findings Model**

- `CIStep.Execute` has the review step's shape: a fix round (`sctx.Fixing`) first repairs the findings the executor selected (`repairFromFindings`, `internal/pipeline/steps/ci_fix.go`), then the monitor runs; every settled observation (no in-scope checks still executing, every authorized transient rerun spent, at least one issue) returns one finding per issue with its action (`ciObservationFindings`, `ci_findings.go`) and the executor's shared loop decides what follows. The step never counts or limits fix rounds; `auto_fix.ci` is enforced by the executor from the round history, which survives `ResetStepsFrom` and daemon restarts. `step_results.ci_fix_attempts` is retired (column kept, never read).
- Classification reads provider structure only: a job verdict (fail bucket) and a merge conflict are `auto-fix` errors; an unresolved transient is `ask-user` (`unresolvedTransientFindings`); a check whose `scm.Check.App` (GitHub `checkSuite.app.slug`) is in `scm.ReviewBots` (Greptile: `greptile-apps`) becomes one `ask-user` warning per unresolved bot comment, bounded (`maxReviewBotCommentFindings`), so it never spends a round. An empty `App` is never a bot. The comment half uses provider-scoped `scm.ReviewBotForLogin`: GitHub matches `greptile-apps` and `greptile-apps[bot]`, while GitLab matches only `greptileai`; only GitHub can attribute a *check* to a bot, so a GitLab run reaches the comment read through the green/not-yet-registered path below and `on_failure` reads nothing there. `scm.Capabilities.ReviewComments` is the opt-in (`GetReviewComments`), true on GitHub (unresolved review threads) and GitLab (unresolved discussion notes: `resolvable && !resolved`, not a system note, bot-authored, diff position for the anchor); a GitLab host without the project path answers `scm.ErrUnsupported` rather than erroring, so it degrades instead of parking. Under opt-in `ci.review_bot_comments: always` (default `on_failure`), each candidate from `scm.ReviewBotCommentChecks`, including informational bots, goes through the same path (`greenReviewBotFindings` -> `ciObservationFindings` with `greenBots`): its unresolved comments are the same ask-user findings and block `checks-passed`, a green bot with none produces nothing, an unreadable comment list withholds readiness and parks after `consecutiveCheckErrorLimit`, and `VerifyApprovalOverride` records an approval over them as an override. The fix agent, not metadata, decides whether an unknown red is about the code: its `code_change_needed=false` conclusion parks the selected findings as `ask-user` (`ciRepairParkOutcome`).
- `types.Finding.Check` (display name), `types.Finding.CheckID` (provider identity), and the `FindingCategoryCI*` constants are the routing keys the fix half reads (`parseCIFixTargets`); `Finding.UnmarshalJSON` and `findingWire` copy fields explicitly, so a new field must be added there or it drops on every parse. Findings ride the IPC event stream, so per-comment findings stay bounded.
- A published repair keeps monitoring inside the same fix round and must call `sctx.MarkRunning()` (executor-owned: durable status back to `running` plus a `step_started` event), or the step stays `fixing` and neither the TUI nor `axi`'s `checks-passed` (`ciReadyToMerge` requires `running`) can surface. The post-repair stale-evidence guard is `lastRepairStillUnverified`: selected checks are snapshotted before a resumed repair, and targets that remain red with neither a newer completion/execution discriminator nor an observed pending state keep the monitor waiting instead of re-escalating. Findings deferred by a fix round survive pending observations and terminal monitor errors until a fresh settled issue set or an established clean result supersedes them.
- Regressions: `TestCIStep_GreptileOnlyRedParksAsAskUserAndSpendsNoAutoFixRound`, `TestCIStep_MixedGreptileAndTestFailureRoutesOnlyTheTestToAutoFix`, `TestCIStep_PublishedRepairResumesMonitoringAndWaitsForTheRerun`, `TestCIResumedRepairSnapshotsSelectedCheckCompletion`, `TestTerminalFailureFreshnessUsesExecutionIDWithoutCompletionTime`, `TestCIStep_PersistentCheckReadFailureParksAtAskUser`, `TestCIStep_UserFixOfTransientFindingIsHonored`, `TestCIObservationFindings_ClassifiesEachIssueByProviderStructure`, `TestExecutor_MarkRunningReturnsAFixingStepToRunning`, `TestExecutor_RestartsValidationFromRequestedStep`, `TestGetChecksCarriesCheckSuiteAppSlug`, `TestParseFindingsJSON_RoundTripsCICheckFields`, `TestCIStep_GreenReviewBotCommentsParkUnderAlways`, `TestCIStep_GreenReviewBotCommentsIgnoredByDefault`, `TestCIStep_GreenReviewBotUnreadableCommentsParkUnderAlways`, `TestCIStep_JobFailureWithGreenReviewBotFollowsThePolicy`, `TestCIStep_VerifyApprovalOverride_GreenReviewBotComments`, `TestCIStep_UnregisteredReviewBotCommentsFollowThePolicy`, `TestReviewBotCommentsOnGitLabFollowThePolicy`, `TestCIStep_GitLabReviewBotDiscussionCommentsParkUnderAlways`, `TestGetReviewCommentsReadsUnresolvedBotDiscussions`, `TestReviewBotRegistry_ResolvesAppAndLoginToTheSameBot`. Step tests drive the loop with `stepstest.ExecuteWithAutoFix` (the executor's auto-fix loop in miniature); a test that calls `Execute` once sees only the observation.
